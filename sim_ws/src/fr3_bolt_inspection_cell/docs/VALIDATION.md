# 验证记录与运行验收

记录日期：2026-09-09。

## 当前已验证

本机为 Windows，无可用 ROS 2 Humble / Gazebo Classic 运行环境。验证使用项目隔离目录中的 Xacro、NumPy 和 SciPy，未改变系统 Python 环境。

- 新包离线测试 **27 项通过**；原双臂包此前的 **35 项测试通过**，包括提供的 3.9.7 驱动源码适配测试。
- 含噪声、只有可见上表面的合成螺丝点云，在四种朝向下能估计位置和头尾；非有限数据、背景、过密数据和多候选被拒绝。
- 所有目标姿态使用右手坐标系；绕估计零件中心插值时，恢复的零件中心保持不变。
- 分段时间满足配置的关节速度、加速度和笛卡尔段平均速度保守约束；实际控制器插值和跟踪仍需仿真确认。
- 三个新增相机的光轴指向目标附近；新增几何有材质、碰撞和惯量；Gazebo/mock 模型中传感器插件正确分离。
- 双臂初始张开姿态的各非豁免链接之间，以及与桌面之间，通过保守 OBB 分离检查。相邻安装结构沿用 SRDF 的局部豁免，没有豁免双臂相撞。
- 默认右手抓取点、上方 50 mm 点、双手同时交接点，以及左手交接前点，找到满足关节限制的数值 IK 解；完整 FK 与目标相符，并通过机器人/桌面 OBB 检查。解保存在 `config/pose_witnesses.yaml`，**只供诊断，任务代码不会直接发送这些关节角**。
- 接收夹爪关闭、辅助夹持、规划场景更新、停稳、位姿核验分别注入故障时，均不会执行原手松开命令。

### 2026-09-09 Ubuntu 首次启动反馈后的修正

首次 Gazebo 日志显示四个手指关节被 URDF 固定关节合并阶段丢弃，随后关节状态广播器因接口不存在而退出；同一 Gazebo 插件中的两个 `ros2_control` 块还重复声明了 `hold_joints`。现已给原本无惯量的 `tool0` 增加小质量和正定惯量，显式保留 `wrist → tool0 → gripper_palm` 固定连接，并把左右臂的 16 个 Gazebo 控制关节合入一个 `GazeboSystem`。mock 模式仍保留左右独立控制管理器。

同一批日志还显示 `inspection_task` 未安装为可执行程序。两个入口脚本现已在 Git 中标记为可执行。更新后必须删除该包旧的 build/install 缓存再重建，不能只重新 `source`。

### 2026-09-10 首次完整任务反馈后的修正

完整日志显示 `APPROACH` 轨迹仍在正常执行时，任务节点在约 78 秒墙上时间后报 `ROS request/action timed out`；控制器在约 119 秒墙上时间后返回成功。四个深度相机降低了 Gazebo 实时率，控制器按 `/clock` 执行轨迹，而原任务节点按墙上时间等待，两个时间基准不一致导致任务在进入 `DESCEND` 前提前失败。现将轨迹控制器和夹爪控制器的完成超时改为按 ROS 仿真时间计算，仅在 `/clock` 连续 30 秒没有推进时按墙上时间判定仿真停滞。全局移动的速度和加速度比例也改为与 `inspection.yaml` 的 0.12 rad/s、0.15 rad/s² 一致，以减少不必要的接近等待。

随后一次运行已越过该超时并进入 `DESCEND`，但 MoveIt 只返回 42.9% 的笛卡尔路径（12 个点），因此任务按设计没有执行部分路径。现已加入每次请求/响应的目标位姿、路径比例、点数、最大关节步长和错误码日志；默认笛卡尔步长从 2 mm 调为 3 mm，关节跳变上限从 0.12 rad 调为 0.20 rad，用于放宽默认俯抓位姿附近的逆解连续性条件。碰撞检查保持开启，完整路径比例仍要求 100%。

OBB 是保守包围盒；盒子分离能证明对应几何分离，盒子相交不能证明真实 CAD 相撞。终点 IK、离线代数测试和合成点云均不能代替完整连续轨迹的 MoveIt / Gazebo 运行测试。

## 需要在 Ubuntu 上实际执行

1. 按 README 构建，确认 C++ 插件编译、安装和加载成功：

   ```bash
   ros2 pkg prefix fr3_bolt_inspection_cell
   ros2 service list | grep /inspection/sim
   ```

   应出现 `left_grasp`、`right_grasp`、`owner`、`get_entity_state`。插件导出路径从安装的 share 目录指向 `../../lib`。

2. 用 `mode:=mock` 看模型，确认两臂镜像、原始 HKV 夹爪和相机支架显示正常。该模式不产生相机数据，任务开始服务应拒绝执行。
3. 用 `mode:=gazebo enable_execution:=true` 启动。先在面板查看四路 RGB，确认腰部相机拍到前下方区域；检查 16 个关节反馈、四路点云、TF 和仿真时钟。
4. 开始任务。检查 `detection.npz` 的点云确实位于螺丝上，而不是桌面或夹指。默认 ROI 对应桌上 `[0.5, -0.2]` 附近的单颗 35 mm 螺丝。
5. 检查上方接近、下降和抬起：下降阶段为完整笛卡尔路径，不得执行仅完成部分的轨迹；夹持未通过几何门限时应停止。
6. 检查定点转动：零件不能绕腕部画大圆；记录实际模型中心与预测中心的误差。当前阈值为 3 mm，加上最初估计中心与模型中心的固定偏差用于扫描中的监控；端点另检查 0.12 rad 姿态误差。
7. 检查交接：先接收手夹住并确认，再原手松开、撤离。确认左手没有从桌面内部接近，并且只有一个辅助固定关节持有零件。
8. 检查左手检测结束后保留夹持、报告实际完成/不可达视角。逐张查看 RGB/深度，确认零件可见；当前只自动检查中心投影在检测相机视野内，**不会自动证明夹爪没有遮挡每个表面**。
9. 分别测试停止按钮、点云中断、关节反馈中断、Gazebo 暂停、相机停止发布、接收手未到位、某个视角规划失败。应取消运动或拒绝开始，不能因失败自动松开零件。

## 需要注意的机构限制

- 默认桌面俯抓解接近腕部奇异姿态。离线检查找到了连续的 50 mm 接近列，但实际 KDL 求解与轨迹插值必须检查关节连续性。当前仿真允许单步关节变化不超过 0.20 rad，并在日志中报告实际最大值；真实机器人使用前应重新收紧并验证该上限。
- 大角度围绕螺丝主轴转动可能因为本体、夹爪或桌面碰撞而不可达。当前允许记录并跳过该视角，每手至少完成 3 个视角；这不保证全面表面覆盖。
- 若运行时失败，优先查看 `report.json` 的第一条失败原因；调整拍摄位置、候选视角或真实机构后重新验证。不要通过大范围禁用碰撞或扩大夹持门限来掩盖问题。
- 15 cm 腕部相机距离只是仿真布局。真实 D435i 的可用近距深度与分辨率、表面反光、曝光等有关；对 35 mm 金属螺丝应实测。腰部固定相机可改用适合近距拍摄的镜头，但这里没有替用户选定实物型号。

## 文件职责

| 文件 | 职责 |
|---|---|
| `launch/bringup.launch.py` | 组装模型/世界，按控制器就绪顺序启动 MoveIt、任务节点和面板 |
| `fr3_bolt_inspection_cell/model.py` | 原始 HKV 网格碰撞、三个相机、支架、光学坐标和世界插件 |
| `core.py` | 点云聚类/PCA、头尾判断、刚体变换、零件中心插值、时间计算 |
| `ros_io.py` | TF、MoveIt 服务/动作、夹爪控制、场景附着、超时与取消 |
| `task_node.py` | 完整流程、数据新鲜度、图像采集、状态与报告 |
| `handover.py` | 可独立测试的交接顺序 |
| `panel.py` | 操作按钮、状态、四路 RGB 预览 |
| `src/sim_grasp.cpp` | Gazebo 几何门限和固定关节夹持辅助 |
| `test/test_core.py` | 离线算法、几何、配置和交接故障回归 |

## 实机迁移前缺项

真实相机驱动/序列号配置、三相机标定、相机与工具负载标定、夹持力或接触反馈、可靠的实物交接判据，以及真实机器人驱动与夹指反馈的一致性，都未在本包实现或验证。原双臂包的 `real` 开关不代表这些功能已经就绪，因此新包没有直接复用 `mode:=real` 自动任务。
